# 02. Требования и правила

[Главная страница](../README.md) · [Связь с проверками](07-verification.md)

Идентификаторы нужны для связи требований, задач и проверок. Ниже не внутренние требования банка и не отчёт о готовом приложении. «Задано» означает вводную владельца; «предложено» — решение этого кейса.

## Правила продукта

| Код | Правило | Основание |
|---|---|---|
| ПП-01 | Фото не передаются на сервер ни для хранения, ни для временной обработки | Задано |
| ПП-02 | Дневник, замеры и прогнозы локальны по умолчанию; согласие на оплату не включает передачу этих данных | Задано; уточнено разделение согласий |
| ПП-03 | Подписка принадлежит человеку и доступна на его устройствах; данные дневника при этом не синхронизируются | Предложено из вводных |
| ПП-04 | Факт тренировки не равен плану; визуализация прогноза не равна достигнутому результату | Предложено |
| ПП-05 | В первой версии покупается 30 или 60 суток вручную, без автоматических списаний | Демонстрационное допущение |
| ПП-06 | Истечение подписки или возврат не уничтожают дневник; чтение и выгрузка доступны | Предложено |

## Функциональные требования

| Код | Требование | Условие приёмки |
|---|---|---|
| ФТ-01 | Регистрация и повторный вход подтверждаются одноразовым кодом | Верный неиспользованный код создаёт сеанс; повтор/просрочка/пять ошибок отклоняются |
| ФТ-02 | Один владелец открывает независимые сеансы на устройствах | Второй вход даёт тот же accountId; завершение одного сеанса не завершает другой |
| ФТ-03 | Сервер задаёт сумму и длительность по тарифу | Клиент передаёт только planCode; цена в теле запроса отклоняется |
| ФТ-04 | Повтор создания платежа не создаёт вторую операцию | Одинаковые владелец, ключ и planCode дают тот же paymentId; другой planCode с тем же ключом — 409 |
| ФТ-05 | Доступ возникает только после сверки с внешней системой | Создание платежа, переход по ссылке и неподтверждённое уведомление доступа не дают |
| ФТ-06 | Один успешный платёж добавляет не более одного периода | Повторный eventId и разные eventId одного платежа не увеличивают срок повторно |
| ФТ-07 | Неизвестный исход не превращается в отказ или новую оплату | После тайм-аута сохраняется creating; повтор с тем же ключом продолжает исходную операцию |
| ФТ-08 | Текущие права вычисляются по неотозванным периодам | На endsAt доступ истекает; будущий период через разрыв не даёт доступ сейчас |
| ФТ-09 | Возврат отзывает период своего платежа | Позднее уведомление не восстанавливает отозванный период |
| ФТ-10 | Объекты защищены принадлежностью учётной записи | Другой владелец получает 404 при запросе чужого paymentId |
| ФТ-11 | Тренировка хранит единицы, исходные данные и версию | Длительность равна сумме отрезков, фактическое время содержит часовой пояс |
| ФТ-12 | Старый расчёт не меняется при изменении профиля | Результат связан с workoutId и sourceRevision, весом на момент расчёта и methodVersion |
| ФТ-13 | Сервер первой версии не принимает дневник или фото | Нет соответствующих методов; лишние поля в разрешённых запросах отклоняются |
| ФТ-14 | Расчёт отделяется от 3D-представления | Модель получает версию и происхождение прогноза; её изменение не меняет численные результаты |
| ФТ-15 | Пропущенные уведомления выявляются повторной сверкой | Подтверждённый у провайдера платёж получает период после сверки |
| ФТ-16 | Ошибка локального сохранения видима пользователю | Приложение не показывает «сохранено», пока запись не завершена; повтор не дублирует workoutId |

## Ограничения качества и безопасности

НТ-01: не писать коды, ключи сеансов, тела с замерами или фото в журналы; не отправлять их в стороннюю аналитику. Проверка сетевых запросов и журналов обязательна перед интеграцией с приложением.

НТ-02: создание периода и регистрация обработанного события атомарны — либо сохраняются вместе, либо не сохраняется ничего. Повторяемость проверяется конкурентными запросами.

НТ-03: время на сервере — UTC; интервалы доступа полуоткрытые [начало, конец). Денежная сумма — целое число минимальных единиц валюты, не число с плавающей точкой.

НТ-04: обработка кода ограничена временем и числом попыток. Демонстрационные значения: 10 минут, 5 ошибок, 5 запросов кода на адрес за 10 минут, сеанс 8 часов. Это не универсальный норматив безопасности; промышленная защита от распределённого перебора и злоупотреблений проектируется отдельно.

НТ-05: «максимальная точность калорий» не принимается как готовое числовое требование. Сначала определяются эталон, виды активности, полнота исходных данных, метрика ошибки и проверочная выборка. До этого обещание процента точности запрещено.

НТ-06: критерии скорости интерфейса и допустимой нагрузки фиксируются после выбора целевых устройств и объёма данных. Нагрузочные результаты отсутствуют; стенд их не подменяет.

## Приоритеты

Первое пользовательское улучшение — законченная цепочка «выбор активности → запись факта → понятный расчёт → базовая 3D-связь с прогнозом». Регистрация и подписка необходимы для платного выпуска. Продвинутую нейросеть не делают обязательным условием проверки первой версии; базовую 3D-функцию не убирают, поскольку это смысл продукта.
