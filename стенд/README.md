# Демонстрационный стенд

[Главная страница](../README.md) · [API](../интерфейсы/openapi.json) · [Сценарии запросов](../интерфейсы/запросы.http)

**Это исполняемая модель аналитических правил, не готовая серверная часть trening.** Целевая технологическая основа приложения остаётся C#/.NET. Python выбран для небольшого переносимого примера контрактов. Это различие нельзя скрывать в портфолио.

## Запуск

Нужен Docker с Compose. Из корня репозитория:

```bash
docker compose up --build -d --wait
```

API: `http://localhost:8080`. Интерактивное описание: `http://localhost:8080/docs` (стандартный интерфейс Swagger использует внешние статические ресурсы; файл `интерфейсы/openapi.json` доступен без них). Имитатор оплаты: `http://localhost:8081`.

```bash
docker compose exec api python -m стенд.сценарий
docker compose --profile test run --rm tests
```

Первая команда показывает регистрацию, повторное уведомление, доступ на втором устройстве и возврат. Вторая запускает проверки схем, правил, HTTP и PostgreSQL. Отдельного входа в приложение trening нет — оно не изменялось.

Остановить без удаления базы:

```bash
docker compose down
```

**Удалить все вымышленные записи стенда**, когда они больше не нужны:

```bash
docker compose down -v
```

## Что действительно работает

Запрос одноразового кода, условная почта, вход на двух устройствах, сеансы, тарифы, создание и чтение платежа, проверка уведомления через отдельный имитатор, атомарное создание периода доступа, возврат и повторная сверка. API действительно использует PostgreSQL; база не добавлена только для иллюстрации Docker.

Дневник проверяется как **локальный формат**, а не отправляется через HTTP. Физиологические формулы не переписываются: пример результата содержит произвольные числа и не доказывает точность расчёта.

## Ограничения и безопасное использование

Принимаются только вымышленные адреса `@example.test`. Письма не отправляются. Ключи в compose — публичные демонстрационные значения, не секреты реальных систем. Порты привязаны к `127.0.0.1`; PostgreSQL не публикует порт. Не размещать стенд в интернете, не вводить реальные данные или реквизиты.

Имитатор хранит платежи в памяти: его перезапуск теряет их; PostgreSQL сохраняет записи. Для повторения чистого сценария пересоздайте стенд с удалением демонстрационной базы. Утрата данных имитатора не должна автоматически признавать старые платежи отменёнными.

Нет настоящей доставки кода, защиты уровня промышленного сервиса, TLS, реальной кассы, периодического планировщика сверки, подписанного разрешения для автономной работы, миграции существующего приложения, нагрузочного и научного испытания. Повторная сверка запускается вручную: `POST /demo/reconcile`, заголовок `X-Demo-Key`. В производственном проекте это внутренняя периодическая работа, не клиентский метод.

Установка зависимостей и образов требует интернета. После запуска демонстрационные сценарии не обращаются к внешней кассе. Теги базовых образов закреплены по основной версии, не по контрольной сумме; для выпуска нужен отдельный контроль цепочки поставки.
